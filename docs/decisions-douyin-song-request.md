# 抖音直播弹幕点歌 → 网易云「下一首播放」

日期：2026-11-08
使用者画像：单人主播，Windows，直播间用「直播伴侣」，Python 可自行装包跑命令行，只给自己用。

## 已确定的约束

| 项 | 结论 |
| --- | --- |
| 地区 | 中国大陆 |
| 规模 | 只服务自己一个直播间 |
| 弹幕来源 | 非官方 WebSocket 抓抖音网页版直播间（选 A） |
| 网易云控制 | 界面自动化操作客户端，「搜索 → 右键 → 下一首播放」（选 A） |
| 点歌触发 | 弹幕里必须带「点歌」关键词 |
| 维护能力 | 能 `pip install`、能跑命令行，出问题能看日志 |

## 方案（已选定）

### 主方案：本地 Python 小工具 + 外部弹幕适配器 + 网易云 UIA 自动化

- 技术栈：
  - Python 3.13（已有）+ `uiautomation`（控制网易云窗口）
  - 弹幕侧不自己重写协议，用 `source = command` 适配器：跑 `DouyinLiveWebFetcher`
    （https://github.com/saermart/DouyinLiveWebFetcher，MIT 风格的「学习交流」项目，2025/2026 仍在更新）
    的脚本，逐行读它的输出，用宽容的字段提取拿到「用户名 + 弹幕内容」。
  - 配置用 stdlib `configparser`（ini），日志落 `logs/`，无数据库、无服务端。
- 为什么适合：主播只要双击一个 `run.ps1`；协议变了自己换弹幕脚本，不用改主程序；
  网易云那步是真实写进客户端播放队列，和他手动点效果一样。
- 开发难度 / 维护成本：主程序低；两个外部依赖会漂——抖音签名协议、网易云界面改版。
  两者都被隔离成「适配器」，坏了只换那一层。
- 目标地区能否顺利使用：能，全程本地、不翻墙。
- 你得自己管的东西：`config.ini` 里填直播间地址；弹幕库克隆在 `vendor/` 下；
  不需要任何密钥、不需要服务器。
- 主要风险：
  1. 抖音网页版接口有签名校验（a_bogus/webmssdk），第三方库随时可能失效 → 已隔离。
  2. 粉丝团/私密直播间、未开播的直播间抓不到评论。
  3. 网易云是 CEF 自绘界面，若 UIA 树取不到控件，需要退回「坐标点击」或换方案 B。

### 备选 B：弹幕用「直播伴侣评论面板 OCR」

截屏直播伴侣的评论区做 OCR，完全绕开抖音接口。最抗封、最不依赖第三方，
代价是中文识别误差（人名/歌名）、要框定区域、分不清进场和评论。
留作 A 失效时的兜底，代码结构已预留（`danmaku` 层是适配器）。

### 备选 C：抖音开放平台「直播小玩法」官方接口

唯一合法稳定的路，但需要开发者资质 + 审核 + 主播每次开播加载小玩法，链路最重。
只在打算做成给别人用的产品时才值得走。

## 推荐：主方案

起决定作用的理由：主播要的是「开播时能跑、坏了能自己换」，
主方案把两个易变点都关进适配器里，主机逻辑（点歌解析、防刷、队列、日志）不跟着漂。

## 仍会改变推荐的待定问题

- 网易云 3.1.42 的窗口能不能被 UIA 读到控件（`doctor` 一跑就知道）；读不到就转坐标点击或方案 B。
- `DouyinLiveWebFetcher` 当前输出格式是否仍是逐行打印（`dump --seconds 30` 会看到）。

## 2026-11-08 现成轮子调研（补充）

查了中文社区和 GitHub 上能搜到的项目，按「能不能直接拿来用」分三层：

### 第一层：完整商业方案（弹幕 → 点歌台 → 播放 → 打赏/积分 → TTS/AI）

- **听云点歌助手 / OBS弹幕点歌助手**（tydgzs.com、obs.wang、obscj.com）
  支持 12 个平台，含抖音。功能：礼物或积分点歌、置顶、切歌、续听、删歌、语音播报、
  冷场讲解、礼物答谢、关键词回复、DeepSeek/通义等大模型回复、横竖版/七宫格/九宫格模板。
  闭源、付费（页面不标价，要加客服微信/QQ 问）。
  **形态是 OBS 浏览器源 + 自带播放器**，不是往网易云客户端队列里塞。
- **咩播（原跨播）点歌插件**
  「唱见版」只记录不播放（给唱歌主播记点歌）；「音乐点播版」自动播放。云端插件、订阅制。

### 第二层：开源的项目（能改，但都不是这条完整链路）

| 项目 | 干什么 | 和我们的关系 |
| --- | --- | --- |
| `saermart/DouyinLiveWebFetcher` | 抖音直播弹幕/礼物/进场抓取 | 已在用，弹幕来源 |
| `SpongeBaby-124/CloudMusic_Auto_Player` | 网易云 MCP 控制器，号称全局快捷键、搜索单曲播放、搜索歌单播放、自定义歌单 | 最接近「网易云点歌轮子」，需验证是否真能插「下一首」、是控客户端还是自己播 |
| `Doctor-Pan-code/ncm-player5` | 网易云浮窗播放器，自带播放队列 | 证明「接管播放」路线存在，但等于不用官方客户端 |
| `imcuttle/request-song-robot` | 网易云点歌机器人（聊天场景） | 思路参考，非直播 |
| B站/抖音「场控机器人」类 | 弹幕姬/答谢姬/回复姬/点歌姬 | 只做队列记录，不碰音乐客户端 |

### 第三层：结论

1. **「弹幕 → 点歌列表 → 界面展示」这层，现成轮子很多，且商业版远强于自建**（积分、礼物、TTS、九宫格）。
   如果目标只是「观众点歌、我按顺序唱/放」，直接买 听云 这类更划算。
2. **「网易云客户端 → 下一首播放」这层，目前没有可直接用的开源轮子**。
   原因是客户端没有公开接口，播放队列是本地状态，只能界面自动化（或换成自己的播放器）。
3. 因此真正的分叉是：**接受点歌助手自带的播放器**（省事，但要换 OBS、要付费、歌不一定全），
   还是**自建、把歌塞进网易云客户端**（免费、歌全、但要维护 UIA 这一层）。
   只有后者才需要本项目。

### 关于「严格格式」

要求观众只用 `点歌 歌名` / `点歌 歌名 歌手` 是对的，但收益不在「减少误触发」
（有关键词过滤已经够了），而在：

- 带上歌手名，搜索命中率明显提高（「晴天」→「晴天 周杰伦」）；
- 格式固定后，解析失败可以直接丢弃，不用兜底，也不会在直播间刷错提示；
- 主播一眼能区分「点歌」和「闲聊」。

它**不会**降低两个真正的风险：抖音协议失效、网易云界面改版。

## 2026-11-08 方案变更：网易云改走原生 IPC（已真机验证）

用户提供了 [BiliNCM-TS / 嗷呜点歌机](https://github.com/Enkianssus/BiliNCM-TS)（MIT）。
它按播放器拆成独立连接器进程（NDJSON 协议），其中 NetEase 适配器暴露了客户端内部的
Orpheus IPC，于是把原来的「界面自动化」整层换掉：

| 动作 | 实现 |
| --- | --- |
| 搜索 | `POST https://music.163.com/api/search/get/web`（form: s/type=1/limit/offset） |
| 下一首播放 | `{"cmd":"playingList","type":"addToNext","value":<id>}` → base64 → `orpheus://…` → 写入共享内存 `orpheus_ipc_<pid>_<tick>` → `SendMessageTimeout(hwnd, 0x8001, pid, tick)` |
| 播放/切歌 | `PostMessage(hwnd, WM_HOTKEY, atom, Ctrl+VK)`，atom 来自 `GlobalFindAtom("play_pause_local" / "next_local")` |
| 现在的歌 | 客户端窗口类 `OrpheusBrowserHost` 的标题「歌名 - 歌手」 |
| 是否插成功 | 读 `%LOCALAPPDATA%\Netease\CloudMusic\webdata\file\playingList` |

**为什么换**：不抢焦点、不依赖控件树、能拿到精确歌曲 id、可验证。UIA 那套只在
客户端改协议时作兜底（`[netease] mode = uia`）。

**真机验证（2026-11-08）**：客户端 3.1.42.205594，当前播放《心痛2009 - 欢子》，
搜索「起风了 买辣椒也用券」→ 选中 id 1330348068《起风了》→ IPC 投递成功 →
`playingList` 确认出现该 id。

**环境坑**：DSH 沙箱是 Low 完整性级别，向 Medium 的客户端发窗口消息会
`ERROR_ACCESS_DENIED(5)`；在普通权限的终端里没有这个问题。

**仍待解决**：抖音弹幕来源（`vendor/DouyinLiveWebFetcher` 未接）。
另外网易云没有周杰伦版权，「晴天 周杰伦」只会搜到翻唱，日志会提示。

## 2026-11-08 抖音弹幕接入：踩到的坑

克隆下来的库结构和网上文章写的不一样：入口是 `liveMan.py`
（`DouyinLiveWebFetcher(live_id).start()`），**没有** `liveWebFetcher.py`；
`live_id` 要纯数字 web_rid，不是整条 URL。

为此重写了适配器 `tools/douyin_ndjson.py`：

- 继承 `DouyinLiveWebFetcher`，只重写 `_parseChatMsg` 输出 JSON；
  礼物/排行榜/进场/点赞全部静音（原库一条排行榜就要 print 十几 KB）。
- 库的 print 全部改道 stderr，stdout 只留 JSON 行。
- 依赖 py_mini_racer 跑 480KB 的 `sign.js`。新 Python 常常没有 wheel，
  于是改成落盘 + `node <file>` 执行（命令行塞不下 32KB）。
  注意 Node 的模块作用域：顶层 `function get_sign` 不在 `globalThis` 上，
  必须按名字直接调用。
- 库用相对路径打开 `sign.js`，所以运行前要 `chdir` 到 vendor 目录。

**验证结果（2026-11-08）**：
- 经本机 7890 代理，WebSocket 连接成功、心跳正常、签名参数生成正常；
- 服务端推送能收到（排行榜、在线人数 699 等）；
- 但两个测试房间都是「几百人在线、零弹幕」的无人直播，没抓到聊天消息，
  聊天解析用构造的 `ChatMessage` 离线验证过，输出为
  `{"type":"WebcastChatMessage","user":{"uid":"123456","nickname":"小明"},"content":"点歌 起风了"}`。
- 仍需在有人气的直播间（或主播自己开播）做最后一次确认。

**其它环境坑**：
- 用户机器上 `python` 指向别名，命令无任何输出 → `run.ps1` 改为
  优先用 `.venv\Scripts\python.exe`，并固定打印所用解释器。
- pip 在 DSH 沙箱里写 `%LOCALAPPDATA%\pip\cache` 被拒（WinError 5）→
  把 `PIP_CACHE_DIR` / `TEMP` 指到工作区后可装。
- `.ps1` 含中文注释必须存 UTF-8 **带 BOM**，否则 Windows PowerShell 5.1 解析失败。
